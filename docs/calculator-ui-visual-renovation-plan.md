# 计算页视觉体系重建：五阶段实施与独立发布计划

**计划版本：V1.0**

**记录日期：2026-09-19**

**文档状态：** 已记录规划，尚未开始实施。写入本文件不代表已执行任何视觉修改、测试、提交或部署。

## 一、目标、边界与阶段划分

### 1.1 已确定的产品决策

本计划采用以下已确认的方向：

1. **只重建计算页面的视觉体系。**
2. 使用**明亮专业工作台**风格：冷灰背景、白色内容面、深石墨文字、深蓝交互色。
3. 允许调整展示结构，包括内容分组、阅读顺序、表格排版和响应式排列。
4. 不改变计算、搜索、选择、保存、优化、参数归一化及数据持久化逻辑。
5. 先统一全计算页公共视觉基座，再完整升级各业务模块。
6. 当前已有工作独立定版、验证后，才开始本计划的视觉升级。

“只重建视觉”具体意味着：

| 可以修改 | 本计划不修改 |
|---|---|
| 颜色、边框、背景、阴影、圆角 | 计算公式、倍率、Buff 生效规则 |
| 字号、字重、行距、数值对齐 | 数值精度、取整和百分比换算 |
| 展示分组、字段位置、表格结构 | 搜索索引、筛选范围、默认选择 |
| 控件的默认、悬停、聚焦、选中、禁用外观 | 取消勾选后的参数保留策略 |
| 弹窗尺寸、滚动容器、底部按钮布局 | 白盒重算时的事件选择逻辑 |
| 同一内容的响应式排版 | 新增“仅看已选”、快捷定位或折叠功能 |
| 用原有状态显示更清楚的视觉标识 | 新增业务状态、接口或存储字段 |

上一轮审查中的行为问题，如覆盖率单位、搜索效果词、取消选择后参数重置、白盒事件跳回，均不作为本计划的实现任务。实施时也不得顺带修复这些行为。

### 1.2 “模块只更新一次”的执行定义

采用用户已接受的方式：

- **阶段一统一公共视觉基础。** 所有模块同时获得最终的基础配色、控件、字体、边界和浮层外观。
- **阶段二至五，每个业务模块只安排一次完整展示升级。**
- 公共基础接入不等于业务模块被拆成两次改版。
- `WorkbenchView.vue` 容纳多个模块，允许不同阶段修改其中各自所属区域；不得跨阶段重复设计同一个业务区域。
- 不安排最后一轮“全页统一美化”补救前面阶段的割裂。
- 每阶段必须在发布前完成自己的桌面、短屏、手机、异常状态和共享组件回归。

“独立发布”指：**在上一阶段稳定版本基础上，当前阶段可以单独上线并长期停留。** 不要求后续阶段能够脱离公共基础任意抽取。

### 1.3 五个正式发布阶段

| 阶段 | 唯一归属 | 同阶段必须完整交付 | 完成后可停留的状态 |
|---|---|---|---|
| 1 | 公共视觉基座与页面外壳 | 主题作用域、全部基础控件、表面、浮层、公共状态、基础响应式 | 全计算页已经拥有一致的新外观，原有信息结构完整可用 |
| 2 | 基础配置与伤害事件 | 角色、音擎、敌方参数、事件摘要、事件管理、技能选择和相关参数表单 | 配置区域完整升级；Buff、驱动盘和结果仍使用阶段一统一外观 |
| 3 | Buff 模块 | 主页面摘要、全部分类、队友选择、Buff 卡片、参数、自定义区域 | Buff 工作流整体升级，其他模块无配套缺口 |
| 4 | 驱动盘与优化模块 | 三种方案来源、六槽位、选盘、保存、限制、优化设置、进度、结果、词条分析 | 中间工作区完整升级，可直接作为成熟版本使用 |
| 5 | 面板与结果模块 | 局外／局内对照、伤害汇总、白盒及全部结果状态 | 五阶段全部完成 |

驱动盘与优化合并为一个阶段，因为它们共用方案来源、优化结果选择、应用与保存流程。阶段内部可以分子任务开发，但必须整体验收后发布。

## 二、阶段一冻结的设计与技术合同

### 2.1 视觉规范依据

采用以下资料中的适用规则，并形成项目自己的规范：

- [Impeccable Operate](https://github.com/pbakaus/impeccable/blob/f2c7051853848826aac2f4646581d62a732155ad/.agents/skills/impeccable/reference/operate.md)：工具界面密度、状态和一致性。
- [Vercel Web Interface Guidelines](https://github.com/vercel-labs/web-interface-guidelines)：清晰边缘、交互反馈、数字排版和可访问性。
- [Google DESIGN.md](https://github.com/google-labs-code/design.md)：同时记录设计数值与使用理由。

阶段一完成后，将规则记录为：

`docs/calculator-design-system.md`

后续阶段只消费该规范，不自行引入新的主色、阴影体系、按钮规格或全页断点。

### 2.2 色彩合同

| 语义 | 固定起始值 | 使用范围 |
|---|---|---|
| 页面底色 | `#EEF1F5` | 计算页内容背景 |
| 主内容面 | `#FFFFFF` | 工作区、主要内容容器 |
| 次级表面 | `#F5F6F8` | 标题带、参数分组、输入区 |
| 主要文字 | `#20252E` | 标题、正文、关键数值 |
| 次要文字 | `#566170` | 说明、辅助标签 |
| 内部分隔线 | `#DCE2EA` | 非交互行分隔 |
| 模块轮廓 | `#B8C1CD` | 工作区与独立内容边界 |
| 控件轮廓 | `#7B8798` | 输入框、选择器等可编辑控件 |
| 主交互色 | `#3154CF` | 主按钮、焦点、当前选择 |
| 主交互悬停色 | `#2746B5` | 主操作悬停 |
| 主交互按下色 | `#223B99` | 主操作按下 |
| 选中底色 | `#EEF2FF` | 当前方案、选中项目 |
| 成功色 | `#16704A` | 已有成功状态 |
| 警告色 | `#8A5712` | 已有警告状态 |
| 错误色 | `#B42335` | 已有错误状态 |

执行约束：

- 颜色先对应语义，再对应组件。
- 游戏属性色、稀有度色和图像素材保留原有含义。
- 重要属性使用清晰的深色文字和字重，避免继续使用浅橙色小字。
- 选中与错误等状态保留文字、勾选或图标，不能只靠颜色。
- 普通文字对比度至少达到 4.5:1；用于识别控件及状态的必要视觉信息至少达到 3:1。
- 非交互装饰线按结构辨识需求设置，不要求全部加深到控件边界的强度。
- 所有实际前景／背景组合需测量，不能仅凭色板通过判断整页通过。

### 2.3 形状、层次与密度合同

| 项目 | 规则 |
|---|---|
| 间距刻度 | `4 / 8 / 12 / 16 / 24 / 32px` |
| 工作区间距 | 默认 `16px` |
| 工作区内部留白 | `12–16px`；同类区域统一 |
| 控件圆角 | `6px` |
| 独立内容卡圆角 | `8px` |
| 主工作区圆角 | `10px` |
| 弹窗圆角 | `12px` |
| 普通边框 | 默认 `1px` |
| 选中强化 | 使用描边或内阴影，避免改变盒子尺寸 |
| 焦点 | 清楚的外轮廓，不能只改变背景 |
| 固定工作区阴影 | 极轻或无阴影 |
| 弹窗、菜单阴影 | 比固定工作区明显，统一方向和色调 |
| 装饰动画 | 移除按钮扫光、持续发光、无意义悬浮位移 |
| 状态过渡 | 统一约 `150ms`；尊重减少动态效果设置 |

字体与控件：

- 中文字体沿用可靠的系统字体栈，不新增远程字体依赖。
- 正文默认 `14px`，说明 `13px`，模块标题 `16px`，弹窗标题 `18px`。
- 关键伤害数值默认约 `32px`，长数字允许适应可用宽度。
- 正文与说明行高约 `1.5`。
- 数字使用等宽数字特性，保持现有精度、单位和格式函数。
- 常规桌面控件高度 `36px`；密集行控件 `32px`。
- 手机常规操作高度至少 `40px`，独立图标操作尽量达到 `44px`。
- 紧凑步进按钮和复选框可以保持较小视觉尺寸，但扩大可点击区域。
- 已有标签、完整说明和校验信息不得因换肤被隐藏。

### 2.4 计算页作用域方案

当前全局主题位于 `webapp/src/App.vue`，不能直接将全局主题替换为新方案。

采用以下固定实现方式：

1. 新增计算路由包装组件 `WorkbenchPage.vue`，仅让 `/` 路由指向该包装。
2. 包装内部放置计算页专用视觉 Provider，再渲染现有 `WorkbenchView`。
3. 使用 Naive UI 的 `namespace="calc-ui"`，同时提供计算页主题。
4. 为计算页消息提供局部 `NMessageProvider`，设置 `container-class="calc-ui"`。
5. 消息 Provider 必须位于 `WorkbenchView` 的父级，使其 `setup` 中的 `useMessage()` 获得局部配置。
6. 计算主题显式重设继承自全局的 Select 边框、背景、阴影和状态，避免残留旧 2px 外观。
7. 所有自定义样式限制在 `.calc-ui` 或计算页专用结构类内。
8. `.calc-ui` 只负责视觉变量与基础外观；页面布局用单独类名，不能向所有浮层容器施加 `overflow:hidden` 或 `transform`。
9. 页面底色通过计算路由专用外壳类应用；切换路由自动撤销。
10. 不给 `body` 设置会残留的全局计算主题。

规划时已核实本地 Naive UI 支持将 namespace 传到弹窗和选择菜单的 Teleport 容器，因此不需要把浮层塞回可能被裁切的工作区内部。实施基线变化后需复核这一兼容性。

### 2.5 新增代码的职责

拟新增文件：

| 文件 | 职责 |
|---|---|
| `webapp/src/design/calculator-tokens.ts` | 颜色、尺寸、字级、圆角与阴影的单一来源 |
| `webapp/src/design/calculator-naive-theme.ts` | 将 token 映射为 Naive UI 主题 |
| `webapp/src/components/calculator/CalculatorVisualProvider.vue` | namespace、计算页主题、消息容器与 CSS 变量注入 |
| `webapp/src/styles/calculator.css` | 只引用 token 的计算页公共样式 |
| `webapp/src/views/WorkbenchPage.vue` | 计算路由包装，不承载业务状态 |

CSS 变量声明从同一 token 对象生成，以 Provider 管理的样式节点提供给 `.calc-ui`，保证 Teleport 内容也能读取。普通样式文件不重复维护另一份色值表。

在 `.calc-ui` 内，将现有结构用途的 `--app-*` 变量映射到新的语义变量，使尚未重排内容的模块立即使用一致外观。

### 2.6 接口与兼容边界

- 不改变后端 API、计算内核、Worker、优化器协议和数据目录。
- 不改变 IndexedDB、localStorage 的名称、版本、键或内容语义。
- 不新增主题持久化字段，不新增明暗主题切换。
- 路由 URL 和路由名称保持不变。
- 共享组件只有需要不同展示结构时，才增加可选的 `appearance="calculator"`；默认继续使用原展示。
- `surface` 等已有属性维持原职责，不能暗中变成主题开关。
- 所有 `props` 业务含义、`emit` 名称和 payload 保持兼容。

### 阶段二：基础配置与伤害事件模块

**目的：** 一次完成角色、音擎、敌方条件和事件配置的展示升级。

主要定位：

- `webapp/src/views/WorkbenchView.vue` 中角色、音擎、计算设置和敌方区域。
- `webapp/src/components/CalculationConfigModal.vue`。
- 其使用的 `EnemyTargetConfigPanel`、`SkillPickerModal`、`LuminescenceEventEditor` 与参数字段组件。

#### 小步骤

**2.1 固定模块边界**

- [ ] Buff 摘要不纳入本阶段。
- [ ] 优化约束与套装条件不纳入本阶段。

| 1366×768 | 常见小桌面 |
| 1280×720 | 短屏与弹窗底部操作 |
| 390×844 | 手机主要场景 |
| 360px、320px 宽 | 长中文与极窄容器压力检查 |
| 真实 125% 页面缩放 | 字体、控件、浮层与断点 |
| 真实 200% 页面缩放 | 内容重排、关键文字和操作可达 |
| Chrome、Edge | 本阶段关键操作与 Windows 字体渲染 |

规划时现有名为 `desktop-125-percent` 的 Playwright 项目使用 `deviceScaleFactor:1.25`，不能代替真实浏览器页面缩放验收。现有 CI 主要覆盖 Chromium，也不能据此宣称已经完成 Chrome、Edge 两者检查。

### 4.3 视觉与交互门禁

每阶段必须全部满足：

- [ ] 页面和弹窗外层无意外横向滚动。
- [ ] 表单标签、当前值、错误、状态和关键结果无裁切。
- [ ] 内容没有被固定底栏遮挡。
- [ ] 关键操作在短屏可以到达。
- [ ] 鼠标、键盘、触摸的既有路径可用。
- [ ] 焦点可见，关闭嵌套弹窗后焦点恢复正常。
- [ ] 悬停、选中、聚焦、禁用的外观不会互相混淆。
- [ ] 选中或错误不会导致布局跳动。
- [ ] 主题覆盖页面、菜单、弹窗、消息。
- [ ] 退出计算页后其他路由没有主题残留。
- [ ] 未升级结构的模块也与已升级模块共享同一基础外观。
- [ ] 没有新增计算页相关控制台错误。

### 4.4 业务不变门禁

使用固定样本比较阶段前后：

- [ ] 角色、音擎、事件、Buff 和优化设置的保存 payload 相同。
- [ ] 显示数值的精度、单位、格式规则相同。
- [ ] 面板及伤害结果相同。
- [ ] 子事件和白盒结果相同。
- [ ] 优化 Top 10 的 ID、排序、分数相同。
- [ ] 取消草稿、保存失败、重试和刷新恢复行为相同。
- [ ] 账号、库存、套装、计算配置未发生非预期写入。
- [ ] 没有新的存储迁移或数据兼容开关。

若发现 B0 已存在的行为问题，登记为独立问题，不混入视觉阶段。

### 4.5 自动验证

每阶段发布前执行：

1. `git diff --check`
2. `npm test`
3. `npm run test:layout`
4. `npm run build:pages`
5. 现有 `CI / verify` 的完整构建、打包和部署契约验证。

说明：

- `npm test` 已包含 Vue 及主要业务回归。
- `npm run test:layout` 会先构建，并运行全部匹配的 E2E 文件，不只是 `layout.e2e.ts`。
- 模块开发过程中先跑相关用例；阶段完成时再跑完整门禁。
- 旧视觉断言应按新规范更新，不能整段删除原有行为验证。
- 不为每个颜色值、边框像素编写镜像式单元测试。
- 新增自动验证重点放在主题隔离、共享组件默认兼容、内容不裁切、浮层可达与展示数据不变。
- 保留每阶段桌面、短屏、手机关键状态截图，不建立不必要的全量像素快照体系。

测试服务器使用独立端口并确认构建来源，避免误用已有旧服务；不为执行验收终止用户当前的本地服务。

### 4.6 每阶段的发布流程

各阶段完成后具备发布资格，实际发布沿用仓库现有流程：

1. 本阶段代码、测试、文档及验收证据形成一个明确交付单元。
2. 集成到 `main`，等待该提交的 `CI / verify` 成功。
3. 记录完整 40 位 SHA、CI run 和同 SHA 的不可变 artifact。
4. `main` 更新本身不部署生产。
5. 实际上线时，通过现有 owner 显式 `Promote deploy` 流程晋级冻结 SHA。
6. 使用 `force:false` 更新部署指针，复用同 SHA 的 CI artifact。
7. 执行现有候选、兼容回滚和健康验证。
8. 原子切换生产 release。
9. 完成计算页本阶段定向 smoke、健康接口、版本 SHA、资源和用户数据检查。
10. 记录当前阶段上线成功；后续阶段从此稳定版本继续。

发布范围为纯 Calculator 网站更新。Helper、Scanner、下载文件、manifest 和 CDN 配置不纳入本计划。

### 4.7 回滚规则

- 每阶段保留上一已验证 release。
- 回滚使用现有生产回滚流程，不强制重写 `deploy` 分支历史。
- 因为没有新增存储 schema，前后阶段继续读取同一套用户数据。
- 回滚后复核健康、版本、计算页及用户数据。
- 保留失败证据，修复以新提交前进。
- 不通过发布下一未完成阶段来掩盖当前阶段问题。

### 5.2 每阶段交付记录模板

每份记录必须包含：

### 5.3 阶段完成的严格定义

只有同时满足以下条件，阶段状态才能改为“完成”：

1. 本阶段所属模块全部展示区域已处理。
2. 不存在“下一阶段补齐”的本模块弹窗或状态。
3. 不依赖后续阶段尚未提交的样式或组件。
4. 整个计算页基础视觉仍然一致。
5. 其他页面及共享组件默认展示未受到非预期影响。
6. 业务结果与持久化契约保持。
7. 验收证据完整，具备独立发布和回滚条件。

阶段状态按以下顺序记录：

`未开始 → 实施中 → 验收中 → 可发布 → 已发布`

“可发布”与“已发布”必须区分，不能将测试通过记录为生产已更新。

### 5.4 任意中途停止时的产品状态

| 停止位置 | 用户看到的内容 |
|---|---|

| 阶段二后 | 基础配置与事件区域完成排版升级，其余区域继续使用统一基础外观 |
