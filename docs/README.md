## 文档格式标准

- **语言**：全部使用中文；代码标识符、命令、路径和协议字段保持原样。
- **头部**：规范类文档第三行写“状态：……。核对日期：YYYY-MM-DD；基准提交：`完整 SHA`。”；角色文件用头部表格的“实现核对”行，另列“资料来源”行。
- **头部的含义**：核对日期和基准提交只代表**最近一次全文核对**，不是最近编辑时间；局部修订不刷新它。来源资料日期、活动周期和版本号写在对应专题或目录数据里，不与实现核对日期混用。核对时记录证据类型（源码静态审查或实际运行的测试），不把旧测试数当作新验证。
- **条款写法**：一条一件事，用“必须/不得”加可检验的结果。不写带日期的“本地扩展（YYYY-MM-DD）”段落，也不写测试数、端口、一次性操作等验证记录（它们属于变更日志）；公式与机制解释放建模说明，回归契约只写不变量和测试入口。
- **链接**：使用相对链接；改标题时同步所有入链和锚点。README 的日期与用户可见事实保持中英文对应。

## 冲突处理

先区分官方机制、已确定的建模假设、管理员当前配置和程序行为。有明确后续决定且实现吻合时更新旧说明；无法确认时在对应角色文件或专题列出“待核实”或“已知缺陷”、复现入口及差异，保留数据，另行处理业务修复。文档任务不得为了让文档成立而改代码或数据。

## 文档验收

- 检查目录、链接、锚点、源码入口、命令和工作流参数；表格单元格里不要出现未转义的 `|`。
- `git diff --check`，并核对差异仅包含本次授权内容，避免整文件换行噪声。
- `npm run test:repository-integrity` 检查资源和 README 必须保留的致谢。
- 发布文档引用的工作流通过 `node scripts/validate-deployment-config.js` 静态核对；该命令不发布生产。
- 文档修改不需要新增业务测试；代码改动仍按对应影响运行必要验证。
